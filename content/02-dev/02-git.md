## 像快照一样追踪修改：Git 与 Git 客户端 {#sec:git}

#### 一句话直觉

Git 给项目做**快照**：每次提交记录"此刻全部文件长什么样"，并记住上一次快照是谁。整条历史是一张只进不退的图——**这就是"可以大胆改"的全部底气**。

#### 提交链：一张只进不退的图

![提交链与分支](figures/src/22-01-dag.svg){#fig:dag}

每个提交是一份快照加一个指向上一个提交的指针。从任何提交出发，都能沿指针走回整个历史——删除、覆盖都做不到。两条平行尝试（分支）可以在各自尽头合并：合并提交有两个"父亲"，同时记得两边[@chacon2014]。

#### 三个区域：改完 → 挑好 → 存档

![工作区、暂存区与仓库](figures/src/22-02-areas.svg){#fig:areas}

日常流程是三步：在工作区乱改（没关系）→ 用 `git add` 把改动**挑**进暂存区 → 用 `git commit` 存档。暂存区的价值常被低估：**它让提交按逻辑分组而不是按时间**——一个提交只讲一件事，是历史可读性的底线。

#### 合并的两种形态

![快进与三方合并](figures/src/22-03-merge.svg){#fig:merge}

主线没动过，指针直接滑到新端（快进）；两边都动了，就造一个有两个父亲的新提交（三方合并）。同一行两边都改了，Git 不猜——它把冲突标出来，**人来裁**。冲突不是故障，是系统在说"这一步需要人类的判断"。

#### Git 客户端：不必背命令

命令行是底层真相，但日常不必全靠它。图形客户端把 add/commit/merge 变成可见操作，IDE 内置的 Git 面板更把"改—看差异—提交"连成一气。**先用客户端建立直觉，命令行随时可以补**——两者操作的是同一个仓库，混用无妨。

#### 可审计：谁、何时、改了什么

每个提交自带**作者与时间戳**——出了问题可以精确回答“这行是谁在什么时候改的”；开启**签名提交**后，每个提交还带一把私钥的签名，收到源码的人可以核验“这份代码自提交者签发后没有被篡改”。快照 + 署名 + 时间线，构成源码的**审计链**——本书样章就是这么做的。

#### 天然短板：快照管内容，不管意图

Git 记得每个版本长什么样，但**不记得为什么**——"为什么这么改"只存在于提交信息里，而提交信息是手写的。历史可读性的上限，取决于提交纪律（一次一事、写清楚为什么）。另一个边界是**文件类型**。Git 的对比与合并按“行”设计，对纯文本最有效：代码、配置、Markdown、LaTeX、CSV 都能逐行追踪；对 MS Office 这类复杂的打包格式基本无能为力；非扫描件的 PDF 带文本层，勉强可追踪，扫描件则与图片无异。二进制文件能存快照但无法逐行对比，仓库还会迅速膨胀——这类内容需要专门的存储方案。

> **常见误解**
>
> 以为"Git 是程序员专用的"。快照 + 指针的模型对任何"会变化的文本"都成立：论文、合同、配置、账本。本书的样章也活在 Git 里——你现在读的每一页，都有完整的修改历史可查。

#### 小结与自检

三句话总结：Git 的历史是一张只进不退的快照图；三区流程让提交按逻辑分组；合并的两种形态里，冲突是留给人的判断题。

自检两题：

1. 为什么"暂存区"能提升提交历史的质量？
2. 两个分支改了同一个函数的不同部分，合并会冲突吗？改了同一行呢？

**数学注解。** 本节无公式。一个结构事实：提交历史是**有向无环图**（DAG）——"无环"保证你沿指针走永远不会兜回原地，这是"历史不会被改乱"的结构性保证。
