## 操作系统也能像代码一样复现：声明式操作系统 {#sec:declarative-os}

#### 一句话直觉

[上一节](#sec:reproducibility)把应用层的可复现解决了；这一层往上推到顶：**操作系统本身也可以声明式管理**。NixOS、GNU Guix 这类系统把"装哪些包、开哪些服务、用户是谁"全部写进一个**配置文件**，整个系统从这一份声明构建出来。

#### 代际与原子回滚

![代际与回滚](figures/src/26-01-generations.svg){#fig:generations}

每次变更生成**新的一代**，旧代原样保留；"当前"只是一个指针。升级出问题？把指针拨回上一代——几秒钟，原子操作，不需要"拆回去"。**大胆升级的底气来自"回滚廉价且完整"**——这与 Git 的提交哲学（[第 2.2 节](#sec:git)）惊人地一致：不可变的历史 + 可移动的指针。

#### 配置与包同源

![同一份声明，三台机器收敛](figures/src/26-02-converge.svg){#fig:converge}

更深的统一：包定义、系统配置、构建脚本用**同一种语言**写成。改一个包的参数，会连带着重新构建依赖它的所有东西——系统与包不会悄悄脱节。同一份配置声明推到笔记本、服务器、救援用的旧机器，三台收敛到相同状态（[图 1-58](#fig:converge)）。

#### 与常规发行版的运维对照

常规发行版的运维是**命令式**的（[第 2.5 节](#sec:reproducibility)）：装了什么、改了哪行配置，散落在机器的历史里；换新机等于重新回忆一遍。声明式系统的运维是**提交**：改声明、构建、切换、（必要时）回滚——[第 2.2 节](#sec:git)的工作流原样适用于整台操作系统。

#### 天然短板：学习曲线与生态边界

声明式操作系统要求你**用它的语言描述一切**——不走它的路，就得不到它的保证。跨出生态（打包一个冷门软件、用一个预设之外的服务）的成本高于常规发行版。工程判断：**可控性要求越高的机器（服务器、基础设施），越值得；高度随性的桌面，未必**。

> **常见误解**
>
> 以为"声明式 = 自动化脚本"。脚本是一串命令，跑完就结束了，机器此后会漂移；声明式是一个**持续的承诺**——系统随时被检查、被拉回声明的状态。区别不在自动化程度，在"终点"是否被显式声明。

#### 小结与自检

三句话总结：声明式操作系统把整机状态写进一份声明；代际机制让升级与回滚都变成原子操作；配置与包同源，三台机器收敛到同一状态。

自检两题：

1. 为什么"回滚廉价且完整"会改变升级的勇气？用[第 2.2 节](#sec:git)的提交哲学类比说明。
2. 什么样的机器不适合声明式管理？（提示：想想"声明"的成本由谁付。）

**数学注解。** 本节无公式。一个结构事实：代际模型把系统状态变成一条**只追加的链**，与 Git 的 DAG（[第 2.2 节](#sec:git)）同构——"不可变历史 + 可移动指针"是可复现性的通用模式，从代码到操作系统反复出现。
